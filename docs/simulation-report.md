# 시범 운영 전 전체 시뮬레이션 보고 (P18)

2026-11-02. 정상 흐름이 아니라 "망가뜨려 보기"가 목적이었다. 로컬(시드·가상 데이터)에서 공격·예외·동시성·한 시즌 재현을 돌렸고, 운영에서는 `[테스트]` 계정으로 로그인·읽기와 실제 AI 4회만 했다(P17-4 확인 1회 포함 총 5회, 상한 30회). 운영 데이터는 지우거나 고치지 않았다.

**수정은 모두 로컬 커밋까지다.** 마이그레이션 2개(`settlement_integrity`, `access_hardening`)는 스키마(정책·함수·색인·뷰) 변경이라 사장님 확인 뒤 원격에 적용한다. 그 전까지 운영에는 아래 P0·P1 문제가 그대로 있다.

## P2 (고치지 않음, 목록만)

1. **오류 화면 없음** — Supabase 장애·서버 오류 때 Next 기본 화면이 뜬다. "잠시 후 다시" 안내 화면(`error.tsx`) 필요.
2. **보안 헤더 없음** — CSP, X-Frame-Options(관리 화면 클릭재킹), HSTS, nosniff, Referrer-Policy.
3. **지난 시간·자정 넘는 강습** — 지난 시간 강습을 등록할 수 있고(직접 의뢰가 바로 만료돼 멈춤), 자정을 넘는 강습은 폼이 막는다.
4. **목록 쪽 나누기** — 강습 목록은 1000건 넘으면 잘리고, 손님 목록은 200명까지만 보이며 "더 있음" 표시가 없다.
5. **샵이 배정·강습을 표로 직접 고칠 수 있음** — 승인된 강습 시간을 다른 달로 옮기는 등. 이제 이중 정산은 색인이 막지만, 배정·강습 쓰기도 RPC 전용으로 줄이는 게 안전.
6. 팀원이 API로 공고 상한가(`jobs.instructor_rate`)는 볼 수 있다(팀 확정 금액은 아님).
7. 입찰과 선정이 같은 순간에 겹치면 이미 배정된 공고에 열린 입찰이 남을 수 있다(잠금 순서). 선정 때 전속 여부를 다시 보지 않는다.
8. 강사 지급액을 비우거나 0·음수로 RPC에 직접 넣는 경우를 막지 않는다. 아주 큰 금액은 원시 DB 오류가 뜬다.
9. 승인 뒤에도 샵 사장이 샵 유형·사업자번호를 바꿀 수 있다.
10. 웹푸시 실패 로그가 오류 객체 전체(구독 주소)를 남긴다.
11. npm audit 중간 9건(exceljs 하위 의존성, 서버에서만 엑셀 생성).
12. 두 탭에서 같은 손님을 등록하면 중복 손님이 생긴다(합치기 제안으로 정리 가능).
13. 390px: 샵 정산 요약 카드가 좁아 "690,000 원"이 두 줄, 강사 정산의 "팀 정산·승인 완료"가 글자 단위로 줄바꿈, 샵 상단 메뉴는 가로로 밀어야 "전속"이 보인다.

## 사장님이 결정할 것

1. **마이그레이션 2개 원격 적용과 배포** — `settlement_integrity`(정산 P0·P1), `access_hardening`(권한 P0·P1). 운영 영향: 데이터 행 변경 0, 정책·함수·색인·뷰만. 운영 정산 항목 3건 중 중복 0이라 고유 색인 생성 가능. 승인 전 샵 0곳. 적용 직후 바로 배포해야 한다(새 화면 코드가 새 뷰·함수를 쓴다).
2. **발행 뒤 승인된 강습 처리 방식** — 지금은 "다음 달 정산서로 이월". 대신 "그 달 정산서를 다시 열어 고침"을 원하면 바꾼다.
3. **전속 강사 원천징수** — 지금은 전속도 프리랜서처럼 3.3%(사업소득). 전속이 근로계약이면 근로소득이라 다르다. 세무 확인 필요.
4. P2 중 시범 전에 고칠 것: 추천은 1(오류 화면)·2(보안 헤더)·3(지난 시간 강습 막기).
5. 이전부터 남은 것: 메일 서비스·도메인(가입 인증·재설정 메일), Supabase 요금제(백업), 테스트 데이터 삭제("삭제 승인"), 강사나·강사라의 스키 제거 여부.
